Local graph names become durable TG identity.

§1Consumers describe a graph with temporary local names; TG assigns opaque UUIDv7s and commits one validated snapshot, or changes nothing.

The mental model. Treat apply_graph as a create-only boundary. It is not a replay API, an update API, or a workflow engine.

§2One graph, two identities

The same three nodes use readable names before the boundary and opaque UUIDs after it.

root is the parent of build; build is the parent of verify. The dashed dependency edges point in the same acyclic direction: build depends on root, and verify depends on build. The example has no self-reference and no cycle. design · graph contract

§3The boundary turns names into durable edges

TG receives generic create fields, resolves each tagged edge target, and returns the mapping that the caller must retain.

The current path is smaller: add::run generates one configurable ID, resolves inputs, pushes one Item, and calls the store writer. Its legacy shape is a short value such as tg-a1b2c; resolve_id also accepts a default prefix and prefix matches. The new direction removes that ambiguity: every new item gets a full lowercase canonical UUIDv7, and lookup validates the whole value before exact matching. The id_prefix and id_len settings are removed rather than ignored. add::run · id

Malformed, prefixed, shortened, or non-v7 input is invalid_id; a valid canonical UUID with no match is item_not_found. Here is the representative request for the running graph. New items have no caller-supplied durable IDs. Only an existing target may carry a durable UUID anchor.

What TG stores after success

Item remains the durable generic shape: status, timestamps, parent, dependency UUIDs, and flattened x-* extension values. TG creates each new item as todo, unclaimed, and unblocked, using one application timestamp. Local names disappear at the boundary.

§4Four phases, one commit

The write lock covers snapshot admission through the single task-file rename, so every failure exits before durable graph mutation.

01 · lock

Lock / snapshot

Acquire Store::with_lock. Load active state and archive IDs. Reject duplicate or malformed durable state before allocation.

02 · map

Generate / resolve

Generate one fresh UUIDv7 per ref. Resolve local through the request map and existing through exact lookup.

03 · prove

Validate graph

Build the proposed active graph in memory. Check item fields, parent rules, dependency rules, and both full-graph cycle sets.

04 · commit

Write once

Call write_atomic once. It writes a temp tasks.jsonl, fsyncs it, and renames it into place.

Any failure stops before rename. Local allocations and proposed items are discarded; no partial mapping is returned.

Outside the commit boundary. Graph apply does not directly mutate:

  • events.jsonl or events.archive.jsonl: creation has no event in the current EventType model.
  • archive.jsonl: existing anchors are read-only, and new items are active.
  • cache.db: a successful task rename makes its freshness stamp stale; open_or_rebuild rebuilds it later.

§5Guarantees and caller limits

TG guarantees a fresh, valid durable graph on success, but it deliberately does not guarantee replay safety after an uncertain response.

ConcernGuaranteeNot a guarantee
IdentityNew IDs are exact lowercase canonical UUIDv7s: 36 characters, version 7, RFC variant.No workflow meaning is encoded in a TG ID.
Existing itemsExisting UUID targets can anchor edges and remain unchanged.Apply cannot update an existing item or edge.
DiagnosticsThe graph_apply error envelope has stable categories, codes, source paths, and deterministic ordering.Discarded generated UUIDs are not exposed in request-local errors.
ReferencesThe result maps every local ref to its new UUID.Local refs are not persisted or accepted by later lookup.
Repeat successEach successful call creates a complete disjoint graph.The same request is deliberately non-idempotent.

Choice ① · retry ownership. An uncertain retry can create a duplicate graph. TG has no application keys, receipts, digests, or deduplication. A caller that needs recovery must own metadata and query-based reconciliation outside TG.

RFC · Decision ③

§6Why TG stays generic

The chosen shape keeps atomic graph storage small and makes workflow interpretation belong to the consumer that owns it.

  • No workflow IDs in TG IDs. UUIDv7 gives opaque identity and optional time ordering. Phase Golem can keep run identity and template node keys in opaque metadata without coupling TG to workflow semantics. Foundation · R4
  • No per-item loop pretending to be atomic. The operation builds the proposed graph first and calls the existing atomic JSONL writer once. CRUD remains the honest path for later individual changes.
  • No TG application keys or receipts. TG reports what it created, not whether a caller's business operation already happened. Consumer-owned metadata can support recovery without teaching TG how to interpret it.

Choice ②Simple authority boundary. TG owns identity, generic edges, validation, and durability. Phase Golem owns run identity, duplicate prevention, and uncertain-result recovery.
