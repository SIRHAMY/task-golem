## Proposal

Split graph storage from workflow interpretation at the existing repository boundary. Task Golem remains the generic authority for task identity, graph state, metadata, claims, events, and the native `todo`, `doing`, `blocked`, and `done` lifecycle. Phase Golem owns templates, run identity, execution policy, executor integration, recovery, and every workflow-specific interpretation of opaque metadata.

Add one TG graph-application operation alongside item CRUD. A request declares only new generic tasks and uses unique request-local symbolic references to connect new tasks before their identities exist. Parent and dependency targets may be either request-local references or full canonical UUIDs of existing TG tasks. Under one TG write lock, TG validates the complete request and proposed graph, generates a UUIDv7 for every new task, resolves every persisted edge to a UUID, and commits all new tasks in one atomic store update. Existing referenced tasks are validated but never mutated. Success returns the complete request-reference-to-UUID mapping; failure commits nothing and returns structured, stable diagnostics through the supported library, in-process, and CLI contracts.

Graph application is intentionally non-idempotent. Every successful call, including an identical repeat, creates a fresh graph with fresh UUIDv7 identities. TG does not accept or retain an application key, request digest, durable apply receipt, or request-local reference, and it does not provide duplicate prevention or uncertain-result recovery. Item CRUD remains the path for changing existing tasks and for adding durable work discovered after a graph has been applied.

PG validates a selected default or user-defined template, resolves its inputs, and compiles the complete declared run graph before calling TG. At run creation it assigns a PG-owned run identity and projects each template node into one independently schedulable durable outcome or human decision. Opaque task metadata records enough PG-owned run, template, node, provenance, ownership, executor-profile, public execution-policy, and verification information to execute the run from its snapshot. Template-local node keys may repeat across runs; TG UUIDs may not. Template edits therefore affect future runs only. Runtime credentials and secrets remain outside TG metadata and outside template snapshots.

PG prevents duplicate materialization by its run identity. Before materialization, and after an uncertain graph-apply response, PG queries generic TG metadata for that run and reconstructs the committed node-key-to-UUID mapping when a complete run exists. PG decides whether another apply is safe; TG never interprets the metadata or changes its fresh-graph semantics. The exact PG-local coordination and reconciliation mechanics are deferred, but they must serialize materialization decisions for one run and distinguish complete, absent, and inconsistent discovered state.

Replace PG's parallel `New`/`Scoping`/`Ready`/`InProgress`/`Parked` lifecycle with TG's native lifecycle, claims, and dependency readiness. PG may retain attempt, session, gate, retry, diagnostic, and provenance facts as metadata or events, but none may form a second task state machine. Planned human gates are ordinary TG tasks marked by opaque PG ownership or executor metadata. PG reports and skips such a ready gate, and dependent work remains unready until an authorized human or wrapper explicitly completes it. `blocked` means execution was attempted but cannot proceed, not that a planned approval is waiting.

TG owns one dependency-satisfaction rule for graph apply, item mutation, readiness, integrity diagnostics, and PG selection. A dependency is satisfied when its target is active and `done`, or when its target is archived with preserved completion evidence; every other active target is unmet. A target absent from both active and archived durable state is invalid, never satisfied by absence. Graph apply and item-level dependency mutation reject new missing targets before writing. Readiness defensively treats any unexpected persisted missing target as unmet, and generic integrity diagnostics including `doctor` report it. Removing a task with active dependents is rejected, while archiving a completed prerequisite preserves enough completion evidence for those dependents. PG consumes this TG-owned result and does not reinterpret archived or missing targets. This decision does not expand parent-edge validation, lifecycle, or rollup semantics.

Templates name logical executor profiles. Trusted PG configuration maps those profiles to local adapters or commands. For each claimed task, PG invokes the selected executor with the snapshotted public policy, accepts a structured `complete` or `blocked` result with a summary and evidence references, runs required deterministic verification, records attempt information, and alone applies the supervised TG transition. Executors never mutate TG directly.

The initial PG supervisor is one foreground, sequential drain-and-exit loop. It selects one ready PG-owned task, claims it through TG, executes and verifies it, explicitly transitions it, and repeats. It stops on idle, a ready human gate, a declared budget or cap, unrecoverable failure, shutdown, or completion of the selected scope. Operators invoke the same loop manually or with external cron/systemd. This Change adds no daemon, internal scheduler, remote-control surface, worker pool, parallel execution, or automatic parent/container/root rollup.

Deliver the repositories in green sequence: first land TG canonical UUIDv7 identity, exact lookup, generic metadata query support, and graph application while preserving item CRUD; then update PG to compile templates and supervise work through those contracts, remove custom-prefix and parallel-lifecycle behavior, and retain only generic reusable execution machinery.

## Decisions

- **Decision 1: TG owns canonical identity, not workflow identity.** TG generates full UUIDv7 task IDs and resolves only exact full UUIDs. Request-local references exist only inside one graph request and response. PG run IDs and template node keys remain opaque metadata because encoding workflow meaning in TG identity would couple generic storage to one consumer.
- **Decision 2: Graph application is create-only and atomic.** One operation validates new nodes, references, parent edges, dependency edges, generic state, and the proposed graph before one commit. Existing UUID targets are read-only. This preserves a simple transaction boundary while item CRUD remains the explicit mechanism for later mutation.
- **Decision 3: Every successful apply creates a fresh graph.** TG omits application keys, digests, receipts, replay detection, and deduplication. This keeps generic persistence free of consumer operation identity; callers that blindly retry an uncertain success accept duplicate graphs.
- **Decision 4: PG owns materialization identity and recovery.** PG places its run and node identity in opaque metadata, queries that metadata before retrying an uncertain apply, and reconstructs the mapping itself. Many runs of one template can therefore coexist without TG assigning semantics to repeated node keys.
- **Decision 5: Templates compile eagerly in PG.** PG resolves inputs and validates the entire declared graph before execution. There is no TG template contract and no lazy runtime generator in this Change. Durable work discovered during execution is added later through TG item CRUD.
- **Decision 6: Run creation snapshots public execution policy and provenance.** A materialized task keeps the policy required to execute that run even if its source template or PG defaults later change. Logical executor profiles are snapshot-safe public identity; trusted command mappings and all credentials remain external PG configuration.
- **Decision 7: One task represents one durable schedulable outcome or human decision.** Executor attempts and internal steps do not become template nodes unless they independently need durable scheduling. This keeps task graph state composable while allowing discovered durable outcomes to become normal CRUD-created tasks.
- **Decision 8: TG lifecycle is the only task lifecycle.** PG removes its `x-pg-status` sub-state machine and schedules from TG status, claims, and dependencies. PG records execution details without redefining readiness or terminal state.
- **Decision 9: Human gates are tasks, not blocked work.** A planned gate remains `todo`, is not claimed by PG, and holds downstream dependencies until an authorized external actor completes it. PG uses `blocked` only after attempted work cannot proceed.
- **Decision 10: PG supervises untrusted execution.** Templates choose a logical executor profile, PG resolves it to trusted local configuration, executors return structured results, and PG performs deterministic verification and TG mutations. Direct executor access to TG would bypass claims, verification, and transition policy.
- **Decision 11: The first supervisor is foreground and sequential.** A drain-and-exit loop provides deterministic claims, transitions, Git use, budgets, and stop behavior without introducing daemon or concurrency coordination. Scheduling remains an external trigger concern.
- **Decision 12: All task transitions are explicit.** Neither TG nor PG automatically completes parents, containers, or roots when descendants finish. Parent edges organize generic tasks; they do not imply lifecycle rollup.
- **Decision 13: TG-009 is source material, not a merge target.** Reuse the generic validation, reference resolution, lock-scoped revalidation, and atomic instantiation ideas from `tg-009-plugin-workflow-supervisor`, but do not preserve its TG-owned templates, persisted instance digest contract, plugin execution metadata, Campaign runner, or container rollup.
- **Decision 14: Cross-repository delivery follows dependency direction.** TG lands and verifies its generic contracts before PG adopts them, so each repository can remain green without a coordinated broken interval.
- **Decision 15: TG owns dependency satisfaction across active, archived, and missing targets.** Active `done` and archived completed targets satisfy dependencies; other active targets and unexpected missing targets do not. TG rejects new missing references and removal of targets with active dependents, preserves completion evidence on prerequisite archival, reports persisted dangling references through generic integrity diagnostics, and supplies the same readiness semantics to PG. PG must not infer that absence means archival or otherwise reinterpret dependency state. Parent semantics remain unchanged.

## Consequences

- A successful TG response is sufficient to identify every created task, but an interrupted response is deliberately ambiguous at the TG operation layer. Consumers without PG-style metadata recovery must not automatically retry unless duplicate graphs are acceptable.
- Request-local references cannot be used for later lookup, replay, mutation, or workflow correlation. Consumers must retain returned UUIDs or place their own correlation data in generic metadata.
- Existing tasks can anchor or satisfy new graph edges without graph apply rewriting them. Any desired change to an existing parent, dependency, status, claim, or metadata requires a separate item operation and its own failure semantics.
- Atomicity covers the durable graph update, so graph application must integrate with TG's lock and atomic JSONL write boundary rather than perform per-item creates. Validation and UUID allocation happen before the single commit; cache state remains derived and rebuildable.
- TG's current query cache does not project `Item::extensions`, so generic metadata query support must expand before PG can recover by run metadata. TG must expose that data without naming or interpreting PG fields.
- The clean UUIDv7 break removes custom prefixes, short-ID lookup, and PG project-prefix identity behavior. No compatibility window or data migration is required, but all current CLI, library, tests, documentation, and PG assumptions must change together within their repository sequence.
- Policy snapshots intentionally duplicate selected template/configuration facts across tasks. This costs metadata space but makes an existing run stable across template edits and supports audit and recovery. Secrets in such snapshots would become durable task data, so adapters must resolve credentials only at execution time.
- Removing PG's parallel lifecycle simplifies authority but changes selection and reporting behavior. Triage/scoping/readiness concepts may survive only as tasks, dependencies, policy, attempts, or diagnostics, never as hidden lifecycle states.
- Human gates may leave an otherwise healthy run idle with a visible ready task. This is expected and distinguishable from `blocked`; an external authorized action is required to resume downstream work.
- Sequential execution limits throughput and avoids parallel Git mutation hazards. External cron/systemd can wake the same finite loop, but long-lived orchestration, remote control, and worker coordination require a later Change.
- Without rollup, parent or summary tasks remain in their current status until an explicit consumer transition. Templates and operators must model any desired summary completion as deliberate work.
- TG-009's unpublished 11-commit branch remains historical. Selective reimplementation reduces risk of importing obsolete ownership assumptions but forfeits a direct merge and requires current-main integration tests.
- Archived completed prerequisites continue to release dependent work without keeping them in the active task set. TG must retain or derive completion evidence across archival and expose one readiness result to all consumers; a dangling dependency instead remains blocked and visible until repaired.
- Dependency writes and removals gain integrity checks at TG's atomic write boundary. A caller must resolve or retain active dependents before removing their target, and PG can no longer treat an item absent from its active input set as implicitly complete.

- What exact Rust request/result types and CLI serialization names best expose graph apply while preserving one semantic contract?
- What generic metadata query/index projection best supports exact PG run reconstruction without coupling TG to PG keys?
- What template serialization, default-template discovery, and file organization best fit PG's current configuration surface?
- What PG-local run-ID generation, process exclusion, and inconsistent-recovery procedure best enforce one materialization decision per run?
- What adapter protocol, evidence representation, deterministic verification interface, and attempt-event shape best fit PG's trusted local execution boundary?
- What internal TG representation and shared evaluation path should preserve archived completion evidence and serve mutation validation, readiness, cache rebuild, `doctor`, and PG without duplicating dependency semantics?
